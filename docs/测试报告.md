## 6. 缺陷清单

### DEF-01：Flyway V4 迁移脚本非幂等（已修复）
- **等级**：P2 中
- **模块**：数据库迁移
- **现象**：`V4__exam_bank_expand.sql` 使用显式 `INSERT` 而非 `INSERT IGNORE`，若迁移中断后重跑，主键冲突导致启动失败
- **根因**：MySQL DDL 无事务，部分执行后无法自愈
- **修复**：手动修复 `flyway_schema_history` 并补插 79 条 question 记录
- **建议**：后续迁移脚本统一使用 `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`

### DEF-02：JWT 无 jti，同秒 Token 相同（P1 高，已修复）
- **等级**：**P1 高**
- **状态**：**已修复（2026-10-02），API 探针 A15 复测 PASS**
- **模块**：认证安全
- **现象**：同一秒内两次登录/刷新签发的 `accessToken` 字节完全相同（无 `jti` 随机声明）
- **影响**：用户 A 在秒级内连续操作时，旧 Token 被拉黑会导致新 Token 同步失效（40103），造成"误伤"
- **修复方案**：`JwtUtil.buildToken()` 增加 `setId(UUID.randomUUID().toString())`（jti 标准声明），确保每次签发 Token 字节唯一
- **复测结果**：同秒并发两次登录返回不同 Token（verify-def-fix.mjs + A15 探针双验证通过）

### DEF-03：X-Forwarded-For 伪造可绕过限流（P1 高，已修复）
- **等级**：**P1 高**
- **状态**：**已修复（2026-10-02），API 探针 I02 复测 PASS**
- **模块**：限流安全
- **现象**：`RateLimitAspect` 与 `AuthController.getClientIp()` 直接信任 `X-Forwarded-For` 头，攻击者可伪造随机 IP 绕过"接口+IP"限流
- **影响**：登录/注册接口可被暴力破解，短信/邮件接口可被轰炸
- **修复方案**：
  1. `RateLimitAspect.buildKey()` 改用 `request.getRemoteAddr()`（真实连接 IP），不再解析 XFF
  2. `AuthController.getClientIp()` 同步改用 `getRemoteAddr()`（登录审计日志记录真实 IP，同时修复 DEF-07）
  3. 新增 `security.rate-limit.multiplier` 配置项：生产环境默认 1（行为不变），dev 环境设为 2 以容纳自动化测试密集调用
- **复测结果**：真实 IP 打满限流桶后，伪造任意 XFF 仍返回 42900（verify-def-fix.mjs + I02 探针双验证通过）
- **部署注意**：若将来部署在 Nginx 等反向代理之后，`getRemoteAddr()` 将拿到代理 IP，需在代理层配置真实 IP 透传（如 `X-Real-IP` + `server.forward-headers-strategy`）并在网关层做白名单校验

### DEF-04：登录错误码可探测账号（P2 中）
- **等级**：P2 中
- **模块**：认证安全
- **现象**：用户不存在返回 `40401`，密码错误返回 `40104`，攻击者可枚举有效用户名
- **建议**：统一返回模糊提示（如"用户名或密码错误"），不区分具体原因

### DEF-05：前端 v-html 渲染题干，依赖前端自觉过滤（P2 中）
- **等级**：P2 中
- **模块**：前端安全
- **现象**：`Practice.vue`、`Exam.vue`、`Wrong.vue` 等 13 处使用 `v-html` 渲染题干/选项/解析，服务端未做 HTML 过滤
- **当前状态**：管理端可录入含 `<img onerror=alert(1)>` 的题干并原样存储
- **风险**：若管理员账号被盗或审核不严，可存储恶意脚本，学员浏览时触发 XSS
- **建议**：服务端对题干/解析做白名单过滤（如 Jsoup），或前端改用 `v-text` + 富文本渲染组件（如 `DOMPurify`）

### DEF-06：无移动端响应式适配（P2 中）
- **等级**：P2 中
- **模块**：前端兼容性
- **现象**：全项目无 `@media` 查询，无移动端 viewport 优化，移动端访问体验差
- **建议**：v1.1 版本增加响应式布局或独立移动端 H5

### DEF-07：登录日志 IP 可伪造（P3 低，已修复）
- **等级**：P3 低
- **状态**：**已修复（2026-10-02，随 DEF-03 一并修复）**
- **模块**：审计日志
- **现象**：登录日志记录的 IP 来自 `X-Forwarded-For`，可被伪造，影响审计准确性
- **修复**：`AuthController.getClientIp()` 已改用 `request.getRemoteAddr()`，日志记录真实连接 IP

## 8. 整体质量评估与建议

### 8.1 质量评估
按维度逐项说说我自己的判断依据：

- **功能完整性**：核心链路（注册登录、刷题、考试、错题、统计、管理端）全部实现，边界校验如题目数量不足、科目不属于题库等都有对应错误码，这项我自己是放心的。
- **代码质量**：分层清晰、响应结构统一；扣分点在于少量硬编码（如默认考试日期写死在两处）和个别魔法值，属于自己知道但不影响使用的债。
- **性能表现**：p95 全部低于 100ms，50 并发无错误，对单机自部署的刷题应用来说余量充足。
- **安全性**：两个 P1（JWT jti、限流 IP 伪造）是这轮测试真正有价值的发现，修复后复测通过；剩余的账号探测和 XSS 过滤问题属于已知取舍，记录在案待改。
- **兼容性**：这是最弱的一项。移动端完全没做响应式，Safari 也只是理论推断，实际投入使用前必须补真机验证。
- **可维护性**：三套测试（63+14+64 例）加自动化脚本，让我后续改代码时敢于动手，这也是个人项目最需要的保险。

综合来看，我认为 v1.0 达到了可上线水平（对应常见的 A- 档）：阻塞项已清零，遗留问题均有明确记录和排期。

### 8.2 上线建议
1. **必须修复（P1）**：已完成（DEF-02 JWT jti、DEF-03 真实 IP 限流，均已复测通过）
2. **建议修复（P2）**：
   - DEF-04：统一登录错误提示
   - DEF-05：富文本 XSS 白名单过滤
   - DEF-06：移动端响应式适配（可排期至 v1.1）
3. **持续监控**：
   - 生产环境部署 APM（如 SkyWalking）监控接口耗时与错误率
   - 定期执行 `tools/api-test/api-test.mjs` 作为健康检查
   - 生产环境部署在反向代理后时，注意 `security.rate-limit` 基于真实连接 IP，需在代理层正确透传
